3일차 최종 배포 및 라즈베리파이 실기기 검증
2026-11-20 | Raspberry Pi 5 | PC 대시보드와 실제 기기 서버

1. 카메라 복구 및 배포 확인
기존 camera-stream.service가 Picamera2 초기화 중 IndexError로 종료되고 재시작을 반복했다. Pi를 재부팅한 뒤에도 카메라 목록에는 “No cameras available!”가 표시됐다.
Pi 전원을 끈 뒤 카메라 리본 케이블을 다시 연결했다. 다음 부팅에서 imx708_wide_noir가 4608×2592 센서로 인식됐다.
Pi가 실행하는 ~/camera_server.py를 제출본으로 교체하고 기존 camera-stream.service를 재시작했다. 서비스가 active가 됐다. D1은 multipart MJPEG를 제공했고, D4와 PC 중계 A9는 최근 발화가 없는 상태(seq=0, 빈 text)로 HTTP 200을 반환했다.
제출본과 실행 파일 모두 SHA-256이 a8bae17acf9e6cf2df88065842e0e2b5d9f8f74ebfe21064d2fd3059cf28c54f였다.
Pi 가상환경에서 로드한 llama-cpp-python은 0.3.35이며 Qwen3-1.7B-Q4_K_M.gguf의 크기는 1,282,439,264바이트였다.

2. D5 도구 선택 및 모델 응답 시간
배포 직후 첫 D5 요청은 모델 로딩을 포함해 48.366초가 걸렸다. 도구 move, 방향 right, 3칸, 빈 message가 반환됐다. 별도 D5 확인 요청도 HTTP 200으로 같은 결과를 반환했다(4.646초).
직접 D5에 ‘앞에 뭐가 있어?’를 보내자 5.0초 뒤 {"tool":"describe","args":{"direction":"left","steps":1},"message":""}를 반환했다. 현재 문법은 describe에도 방향·칸 수를 허용한다. PC의 parse_tool_call은 describe의 인자를 {}로 정리하고 최종 답변에는 장면 인식 결과를 사용한다.
검증 디렉터리에서 다음 명령으로 측정했다.
python API_검증.py --timings --device <PiIP>
객체 검출·장면 설명은 sample.jpg(810×1080), 도구 선택은 ‘오른쪽으로 3칸 가’와 빈 대화 기록을 사용했다. 시간은 HTTP 송수신과 서버 처리를 포함한 초 단위다. 평균은 예열 1회를 제외한 3회 응답의 평균이다.

| 모델과 API | 예열 | 1회 | 2회 | 3회 | 평균(초) |
| --- | ---: | ---: | ---: | ---: | ---: |
| YOLO11n · PC A3 | 0.088 | 0.025 | 0.025 | 0.026 | 0.026 |
| Qwen2.5-VL-3B · PC A4 | 4.206 | 4.120 | 4.229 | 4.336 | 4.228 |
| Qwen3-4B · PC A5 | 1.992 | 1.786 | 1.760 | 1.779 | 1.775 |
| Qwen3-1.7B · Pi D5 기존 | 15.994 | 16.184 | 17.419 | 16.784 | 16.796 |
| Qwen3-1.7B · Pi D5 최종 | 5.732 | 3.331 | 3.792 | 3.043 | 3.389 |

기존 D5는 반환할 문장까지 생성했다. 최종 D5는 GBNF로 message를 빈 문자열로 제한하고 모델이 도구·인자를 선택하게 했다. 같은 문맥에서 예열 후 평균이 13.407초(79.8%) 줄었다. 배포 직후 첫 요청은 예열 및 세 차례 반복 측정과 별개다.

3. 기능 검사 및 물리 출력
첫 오프라인 오류 주입은 19/19 PASS였다. R9 실패를 반영해 명령과 장면 질문을 구분하는 회귀 사례 7개를 추가한 뒤 26/26 PASS를 확인했다. 잘린 JSON, 범위를 벗어난 인자, 방향 확인, D5 통신 실패와 복구도 포함한다.
PC 모델 포함 검사는 PC 규칙 수정 전후에 각각 98/98 PASS였다. 객체 검출·장면 설명·도구 선택과 입력 오류를 포함한다.
최종 PC 서버의 --quick 검사는 22/22 PASS였다. A1~A9의 입력 오류와 연결 실패 응답을 확인했다.
기기 입력으로 LEFT → UP → RIGHT → DOWN 이동을 처리했다. PC 중계 A8의 OLED 요청 4건, A7의 좌우 LED 요청 2건이 모두 HTTP 200을 반환했다.
두 번째 출력 시연에서 각 OLED 방향을 8초간 유지했다. 사용자가 LEFT, UP, RIGHT, DOWN 네 표시와 왼쪽·오른쪽 LED가 각각 세 번 깜박이는 것을 확인했다. PASS.
같은 출력을 재현하려면 검증 디렉터리에서 아래 명령을 실행하고 Enter를 누른다.
python OLED_LED_육안_검증.py --device <PiIP>
사용자 요청에 따라 PTT 녹음, 실제 발화, 새 음성의 STT 전사는 이번 검증에서 제외했다.

4. 기기 드라이버·입력 규칙·서버 재시작 검증
Pi의 D3 드라이버에 보낸 GET /oled-display?text=RIGHT는 HTTP 200과 oled=shown을 반환했다. 문구 없는 요청에는 HTTP 400을 반환했다. 이 항목은 위에 기록한 사용자의 육안 관찰과 별도로 측정했다.
최종 배포 직후 첫 전체 --device 검사는 202/205 PASS였다. 실패 3건은 모두 R9의 음성 인식 결과를 모사해 A5에 보낸 이동 명령이었다. ‘버스 있는 쪽으로 가’와 ‘버스 위치로 가’는 방향을 되묻고, ‘위 2칸 가’는 위로 2칸 이동해야 했지만 세 요청 모두 describe를 반환했다.
R9 보완 후 전체 --device 재검사는 205/205 PASS였다. A1~A9, D1~D5, F301·F302와 R1~R10을 포함한다. R9는 13/16에서 16/16으로 회복했다.
PC 공통 규칙을 고쳐 Pi가 describe를 골라도 명시적인 이동 명령이면 방향 근거에 따라 이동하거나 되묻게 했다. 물체 이름과 ‘위치’는 방향 근거로 쓰지 않는다. 오프라인 검사에서는 ‘가지 마’, ‘어디로 가?’와 장면 질문이 이동으로 처리되지 않는지도 확인했다.
같은 세 입력을 기기 경로에 다시 보낸 결과는 순서대로 ask(1칸, 3.3초), move(up, 2칸, 3.7초), ask(1칸, 4.3초)였다.
브라우저에서 실제 Pi 서비스 중단과 복구를 확인했다. 같은 페이지에서 기기 탭의 ask(2칸) 직후 서비스를 정지하자 후속 입력은 HTTP 502(device_llm_unreachable)를 받았다. 대화 기록은 2개였고 출력 요청은 0건이었다. 장애 중에도 로컬 PC 탭은 move(right, 1)로 HTTP 200을 반환했다.
Pi 서비스를 다시 시작한 뒤 기기 탭은 기존 기록 2개로 move(left, 2)를 확정했다. A8·A7 모두 HTTP 200이었고, 다음 장면 질문은 빈 기록으로 describe를 받았다. 실제 카메라 영상은 중단 전·복구 후 모두 640×480이었다.
수정 후 구동한 PC 서버(8000 포트)에서 버전 관리한 실기기_브라우저_장애_검증.cjs로 같은 장애를 다시 주입했다. 두 단계 모두 PASS였고 종료 코드는 0이었다. 서비스 중단 중 기기 502·로컬 200·출력 요청 0건, 복구 후 실제 영상·왼쪽 2칸 대화·A8 및 A7 HTTP 200·새 질문의 빈 기록을 검사했다. 마지막으로 Pi의 camera-stream.service가 active/running임을 확인했다.
PC 서버를 별도 포트에서 두 프로세스로 차례로 실행했다. 첫 프로세스(PID 12648)에 ‘저쪽으로 2칸 가’를 보내 ask(2칸)를 받은 뒤 같은 브라우저 페이지를 유지한 채 서버를 재시작했다. 두 번째 프로세스(PID 35992)는 기존 대화 기록 2개와 ‘왼쪽’을 받아 move(left, 2)를 확정했다. 실제 Pi의 OLED·LED 요청도 모두 HTTP 200이었다. 이 시험에서 테스트 탭의 영상 요청만 차단했고, D5와 물리 출력은 실제 Pi를 사용했다.
실제 영상이 켜진 기본 대시보드(127.0.0.1:8000)에서도 재검증했다. ‘저쪽으로 2칸 가’에 되묻기를 받은 상태로 PC 서버를 종료했다. 8000번 포트의 연결 거부와 영상 끊김 표시를 확인한 후 새 PC 프로세스를 시작했다. 페이지를 새로고침하지 않은 상태에서 실제 Pi 프레임이 다시 표시됐고, ‘왼쪽’이 기존 기록 2개를 사용해 move(left, 2)로 처리됐다. A8·A7 모두 HTTP 200이었고 브라우저 검사는 종료 코드 0으로 끝났다.
