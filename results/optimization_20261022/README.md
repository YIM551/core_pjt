# 대시보드 병목 측정 및 최적화

측정 환경: 기존 CPU 환경, 동일 Furniture best.pt와 테이블 JPEG, YOLO/VLM 병렬 호출 뒤 답변 엔드포인트 호출. 모델이 준비된 상태에서 각 3회 측정했다. 프로세스 기동 및 가중치 로딩은 표의 수치에 포함하지 않는다.

| 서버 API 구간 | 변경 전 중앙값 | 최적화 후, 캐시 끔 |
|---|---:|---:|
| YOLO | 0.050초 | 0.046초 |
| VLM | 7.082초 | 7.270초 |
| 후속 답변 구성 | 2.623초 | 0.002초 |
| 전체 | 9.705초 | 7.272초 |

전체 약 25.1% 단축. VLM은 빨라진 것으로 해석하지 않는다. 이 실험에서 제거한 주요 비용은 최종적으로 사용하지 않는 LLM 답변 생성이다. F206이 출처 포함 장면 답변을 결정적으로 구성하는 좁은 질문 집합에만 빠른 경로를 적용했다. 이동·복합 질문·새로운 의도는 기존 LLM과 도구 규칙을 사용한다. API 응답의 inference_path로 구분한다.

VLM exact-input 캐시는 최대 8개의 텍스트 결과만 메모리에 보관하며 TTL은 60초다. 키는 디코딩된 이미지의 모든 픽셀·크기·모드·프롬프트·입력 제한·토큰 제한이다. 실패 결과는 저장하지 않으며 프로세스를 재시작하면 사라진다. 같은 프레임에 대한 동시 생성도 한 번만 수행한다. 다른 프레임은 새로 추론한다. 현재 프로세스에서 모델 경로는 시작 시 고정되고 모델/설정 교체 시 재시작해야 한다.

캐시를 켠 첫 테이블 요청은 7.322초(캐시 미적중), 이어진 동일 입력 요청은 0.039초·0.047초였다. 이는 새로운 이미지 추론 속도가 아닌 동일 결과 재사용이다. 캐시가 있는 실제 새 브라우저 첫 전송은 2.426초였으며 브라우저의 MediaPipe 초기 처리와 캡처·DOM 비용을 포함한다. 브라우저 시간과 서버 API 시간을 직접 비교하지 않는다.

화면 단계별 고정 550ms 대기를 제거했다. 기존 일반 설명 흐름에는 캡처 후·분석 후·답변 후 총 1.65초의 강제 대기가 있었으며, 현재는 실제 작업 완료에 따라 진행한다. 추가 이동/되묻기 단계에서도 고정 대기를 없앴다.

같은 입력 해시, 원시 YOLO 검출, VLM 설명, 최종 답변과 F206 미확정 안내가 유지됨을 comparison.json의 12개 검사로 확인했다. 최적화 단위 검사 6개와 F206 검사 5개도 통과했다. 실제 브라우저 검증과 화면은 browser/에 있다. 기존 API 검증 로그는 api_validation.log에 있다. 1장·3회 측정이므로 여러 장면이나 다중 사용자 부하에 대한 성능 보장은 아니다.

실행은 기존 scripts/start_furniture_dashboard.ps1을 사용한다. A/B 확인은 서버를 시작하기 전에 CORE_SCENE_FAST_PATH=0으로 빠른 경로를 끄거나 CORE_VLM_CACHE_SIZE=0으로 캐시를 끈다. 기본값은 각각 1과 8이다. 원상복구 시 환경변수를 제거하고 서버를 재시작한다. 벤치마크는 scripts/benchmark_dashboard.py, 결과 비교는 scripts/compare_optimization.py를 사용한다.

남은 주요 병목은 새 프레임의 VLM 추론이다. 입력 축소·출력 토큰 제한·스레드 수 조정은 정확도와 응답 형식에 영향을 줄 수 있어 이번 변경에서는 유지했다.
